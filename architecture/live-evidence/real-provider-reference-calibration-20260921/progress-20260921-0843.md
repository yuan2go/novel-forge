## 3. 为什么耗时这么久

1. **原链路的缺口比单个 Router 改动深。** 缺的不是一个模型开关，而是未合格候选如何采样、reviewer 如何独立冷启动、如何从真实回执形成准入证据，以及如何不污染正式接纳。这些边界确实需要工程修复。
2. **我采用了低效的局部推进方式。** 多次按“发现一个缺口 → 修补 → 定向回归 → 更新 proposal/Reality → 再发现下一个缺口”推进，没有尽早把完整最小闭环和所有剩余阻断一次收敛。产生了有用代码，也导致大量碎片化迭代。这是主要的执行管理问题。
3. **不同实现版本反复验证，旧门禁不能继承。** 先前 SHA 的完整 P0 已跑过，后来继续修改代码、评价和预算契约，就必须重新测试。数据库集成、迁移与恢复耗时明显；不能把旧 SHA 的 PASS 算到当前版本，但我应更早固定实现边界，减少反复。
4. **文档和证据维护过于频繁。** 28 个提交中有 13 个属于文档或证据。仓库确实要求生命周期与版本身份准确，但可以更合理地批量收口，不应让这种维护掩盖主链仍未运行的事实。
5. **并发发布带来额外身份整理。** 早期共享 worktree 的变更被另一个汇总流程发布，后来迁入独立 clone，并核对 main 与实现树。它增加了工作量，但不足以解释全部耗时，也不是当前主要阻断。
6. **缺少付费授权只解释为什么没有真实调用，不能解释全部开发时长。** 仍有不付费工程未完成，责任不能推给用户未授权。

Git 可核实，这 28 个本地提交的提交时间从 2026-09-20 23:54 到 2026-09-21 07:56，跨度约 8 小时；这不是整个会话的精确工时，也不能据此精确分摊编码、等待、重试和模型推理时间。没有足够计时数据给出可信的百分比分解。
